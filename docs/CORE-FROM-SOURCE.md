# Building realm-core from source

`@pomwik/afterdb` ships the prebuilt realm-core engine of the official Realm® JavaScript SDK package `realm@20.2.0`
without recompiling it (`bridge/build.mjs`). If a new NDK or Xcode, or a CVE fix, ever needs a change inside the
engine, it has to be rebuilt from its source. This page gives the steps that were run and their results. The last
section lists what was not checked. Nothing here changes the published package.

Realm® is a trademark of MongoDB, Inc. afterdb is independent and not affiliated with or endorsed by MongoDB.

## Which realm-core

| | |
|---|---|
| realm-js commit of `realm@20.2.0` | `cf86fe01fd5f0aec603c77abdfb187ce5982faf2` ("[20.2.0] Bump version"): `npm view realm@20.2.0 gitHead` |
| realm-core commit | `15493076ad9fef22c16cc64cbfbf9e5b65c385f9`, tag `v20.1.0`: the submodule `packages/realm/bindgen/vendor/realm-core` at that realm-js commit |
| realm-core version | `20.1.0` (`dependencies.yml`, which also says `OPENSSL_VERSION: 3.3.1`; realm-js has no `dependencies.list`) |

- The git tag `v20.2.0` of realm-js points to `5064bb5`, a commit whose `packages/realm/package.json` says `12.15.0`
  and whose realm-core submodule is `cccb3ca` (14.14.0). It is not the commit npm published 20.2.0 from.
- Check, done on the package files: the 202 headers of `prebuilds/android/arm64-v8a/include` in `realm@20.2.0` that
  exist in realm-core's `src/` are byte-identical to `src/` at `15493076`. The two others, `realm/version_numbers.hpp`
  (`20.1.0`) and `realm/util/config.h`, are generated by CMake. `bindgen/vendor/realm-core/bindgen/src/realm_helpers.h`
  is identical too.

## How upstream built it

`packages/realm/src/scripts/build/android.ts`, `apple.ts` and `xcode.ts` at `cf86fe01`, run by the `prebuild-android`
and `prebuild-apple` jobs of `.github/workflows/pr-realm-js.yml`:

- Android: `ubuntu-latest`, CMake 3.29.2, NDK 27.1.12297006, API 24, `Release`, `c++_shared`, C++20,
  `REALM_BUILD_LIB_ONLY=ON`, ccache. Only `librealm.a`, `librealm-object-store.a` and `librealm-parser.a` are kept.
- Apple: CMake's Xcode generator with realm-core's `tools/cmake/xcode.toolchain.cmake`, `xcodebuild archive` per SDK,
  `libtool -static` into `librealm-combined.a`, then `xcodebuild -create-xcframework`. The script expects Xcode 15.4;
  the prebuilt simulator objects record SDK 17.5 and minimum iOS 14.0 (`vtool -show-build`).

## The scripts

| File | What it does |
|---|---|
| `scripts/core/fetch-core.sh <work>` | Clones realm-core at `15493076` (depth 1) with the submodules `src/external/sha-1` and `src/external/sha-2`, checks the commit and `VERSION: 20.1.0`, and resets the sources. With `AFTERDB_CORE_PATCHES=1` it then applies `scripts/core/patches/*.patch` |
| `scripts/core/patches/` | Two source changes that Xcode 26.6 needs (see Results). Android builds do not use them |
| `scripts/core/build-android-core.sh <afterdb package> <work> [abi]` | Upstream's CMake options for Android. OpenSSL is the archive inside the afterdb package (SHA-256 checked against the value the package records), unpacked where realm-core's CMake looks before downloading: nothing comes from static.realm.io. Output: `<work>/install-android-<abi>/{include,lib,share}`, the layout of `prebuilds/android/<abi>` |
| `scripts/core/compare-android-core.sh <afterdb package> <install> [abi]` | Sizes, archive members, defined and undefined global symbols (`llvm-nm` of the NDK), headers and CMake files, against the package |
| `scripts/core/build-ios-sim-core.sh <work> [arch]` | Upstream's Apple steps for the `iphonesimulator` SDK and one architecture. Output: `<work>/librealm-combined-iphonesimulator-<arch>.a` |
| `scripts/core/compare-ios-sim-core.sh <afterdb package> <lib> [arch]` | Size, members and symbols against the same architecture of the package's simulator slice |
| `.github/workflows/core-from-source.yml` | Runs the above on GitHub Actions, puts the result in the published package, builds the example app with it and runs the self-check |

Differences with upstream on Android: CMake 3.22.1 (Android SDK package) instead of 3.29.2, no ccache, and OpenSSL
3.5.9 (afterdb's archive) instead of 3.3.1. The runners had bison 3.8.2 and flex 2.6.4, the exact versions realm-core
asks for, so CMake regenerated `src/realm/parser/generated/query_bison.cpp` and `query_flex.cpp`. Without them it uses
the copies committed in realm-core.

## Commands

Android, one ABI, as the workflow runs them (`ubuntu-24.04`, Android SDK of the runner):

```sh
npm pack @pomwik/afterdb@20.3.0 --pack-destination pkg   # integrity checked against npm in the workflow
tar -xzf pkg/pomwik-afterdb-20.3.0.tgz -C pkg
sdkmanager --install "ndk;27.1.12297006" "cmake;3.22.1"
bash scripts/core/build-android-core.sh pkg/package "$RUNNER_TEMP/core" arm64-v8a
bash scripts/core/compare-android-core.sh pkg/package "$RUNNER_TEMP/core/install-android-arm64-v8a" arm64-v8a
```

To use the result, replace `include/` and `lib/` of `prebuilds/android/<abi>` in the package with those of
`install-android-<abi>`, and keep `share/` and `deps/` (afterdb's CMake changes and OpenSSL). The app's Gradle build
then compiles the binding (`librealm.so`) against them as usual.

iOS simulator, arm64 (`macos-26`, newest released Xcode 26.x picked by `scripts/ci-xcode.sh newest`):

```sh
AFTERDB_CORE_PATCHES=1 bash scripts/core/build-ios-sim-core.sh "$RUNNER_TEMP/core" arm64
bash scripts/core/compare-ios-sim-core.sh pkg/package "$RUNNER_TEMP/core/librealm-combined-iphonesimulator-arm64.a" arm64
lipo pkg/package/prebuilds/apple/realm-core.xcframework/ios-arm64_x86_64-simulator/librealm-combined.a \
  -replace arm64 "$RUNNER_TEMP/core/librealm-combined-iphonesimulator-arm64.a" -output combined.a
```

- OpenSSL: CMake found the afterdb archive (`found version "3.5.9"`), and `librealm.a` calls the same 17 OpenSSL
  functions as the prebuilt one (`EVP_*` and `HMAC`).
- CMake files: `RealmTargets.cmake` and `RealmTargets-release.cmake` differ only in the boilerplate CMake writes
  (3.22 here, a newer CMake upstream). `RealmConfig.cmake` asks for OpenSSL 3.5.9.
- The libraries are not byte-identical. Each one holds the absolute source paths of the machine that built it, and
  those paths differ (`/home/runner/work/realm-js/realm-js/packages/realm/bindgen/vendor/realm-core/src/` upstream,
  `/home/runner/work/_temp/core/realm-core/src/` here). Nothing else about the difference was checked.

The example app (React Native 0.88.1, release build, one ABI) built with this engine in the published package:

- Gradle build OK for both ABIs. `node_modules/realm` held the libraries built here (`cmp`).
- `librealm.so` in the APK has 36 source paths of this build and none of upstream's build, so the engine in it is
  the one built here. Size: arm64-v8a 9,109,944 bytes, x86_64 9,751,320 bytes. The APK of main run 42716333335
  (prebuilt engine): 9,114,040 and 9,751,320.
- arm64-v8a `librealm.so` against the one of run 42716333335, checked locally with the NDK's `llvm-nm -D` and
  `llvm-readelf -d`: same 7,386 exported and 430 imported dynamic symbols, same `NEEDED` libraries.
- All 64-bit native libraries of both APKs are 16 KB aligned (`scripts/check-16kb.mjs`).
- x86_64 on an Android 16 emulator (API 36, `google_apis`, x86_64) in CI: `AFTERDB_SELF_CHECK_OK` on launch 1 and
  launch 2 (`scripts/android-selfcheck.sh`, no retry needed).
- arm64-v8a on a local Android 16 emulator (API 36, `google_apis_playstore` arm64-v8a image, Apple silicon Mac),
  with the APK of run 42724560193 (SHA-256 `cf50734c243e8579cd176bd1b0d8528a48e314dde27ed746ee30e375d4d7e564`):
  `AFTERDB_SELF_CHECK_OK` on both launches, 13 checks including `encryptedReopen` and `encryptedNeedsKey`.
- Same local emulator, same app id and signing key: the APK of run 42716333335 (prebuilt engine) installed first
  showed `launches: 1`; the APK with the engine built here, installed over it with `adb install -r`, showed
  `launches: 2`; the prebuilt APK installed again showed `launches: 3`. All three showed `AFTERDB_SELF_CHECK_OK`.
  This covers one plain file (`launches.realm`, one counter). The self-check deletes and re-creates its encrypted
  file at each launch, so no encrypted file was opened by the other engine.

### iOS simulator, arm64

- Run 42726972499, unchanged sources, Xcode 26.6 (17F113), CMake 4.4.5: build failed with
  `'is_pod' cannot be specialized: Users are not allowed to specialize this standard library entity` in the s2
  headers (the same cause as realm/realm-js#7115), then, with that fixed,
  `no member named 'strtol' in namespace 'std'` in `src/realm/util/cli_args.cpp`.
- Run 42728483279, with `scripts/core/patches/0001-s2-no-std-is_pod-specialization.patch` (same change as the one
  afterdb already ships in the xcframework headers) and `0002-cli_args-include-cstdlib.patch` (adds
  `#include <cstdlib>`): `ARCHIVE SUCCEEDED` with no other compile error. `build-ios-sim-core.sh` took 4 min 25 s
  (clone, configure, build).

each side (printed in the job log) are mostly constructors, destructors and template instantiations, which a compiler
can inline or emit differently; the undefined ones are libc++ functions plus `acosl` and `wmemchr`. The other names
were not looked at.

The example app with this slice (`lipo -replace arm64`, the x86_64 slice left prebuilt), no frameworks,
Release, `macos-26` runner:

- Simulator build OK. The app holds 118 source paths of this build and none of upstream's.
- iPhone 17 Pro simulator, iOS 26.5: `AFTERDB_SELF_CHECK_OK` on launch 1 and launch 2 (`scripts/ios-selfcheck.sh`).

## Not verified

- The published package is unchanged: it still ships upstream's prebuilt engine for every platform.
- Android armeabi-v7a and x86: not built.
- iOS device (`ios-arm64`), iOS simulator x86_64 and Mac Catalyst slices: not built. The xcframework was not rebuilt
  with `xcodebuild -create-xcframework`; only the arm64 simulator slice was swapped.
- iOS on Xcode 26.4: not tried. The patches were only tried with Xcode 26.6.
- With frameworks (`USE_FRAMEWORKS=static` or `dynamic`): not tried with the engine built here.
- The Node binaries (`prebuilds/node`): not built from source.
- The Android build on macOS: not run. The Android builds above ran on `ubuntu-24.04` runners; the Mac was only used
  for the arm64-v8a emulator run and the `llvm-nm` comparison.
- Real devices: not run.
- realm-core's own test suite: not built or run (`REALM_BUILD_LIB_ONLY=ON`).
- Byte-identical rebuild of the prebuilt files: no (see sizes).
- Opening an encrypted file written by one engine with the other: not tested.
- A change of the engine itself (a CVE fix, for example), and how it would be released: not done. Shipping an
  engine built here would also need all ABIs and slices, and an update of `THIRD-PARTY-NOTICES.md` and
  `CHANGES-FROM-UPSTREAM.md`.
